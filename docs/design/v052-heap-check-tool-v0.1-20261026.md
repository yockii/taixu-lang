# 用户可用的堆检查：`--heap-check` 与对象号隔离（v0.1，2026-10-26）

来源：用户 2026-10-26 裁决第 2 项（跟进第 26 条）——对象号被复用后的过度释放只在测试与调试形态查，发布零开销，并须有用户可用的
快速检测工具。

## 一、现状

1. 对象以对象号引用：值 `{tag@0, idx u32@8}`，引用计数在按号索引的表里——槽表状态的“标志数组”即计数表（分配时置 1）。归零经
   `__tx_zero_dispatch(idx)` 回收，`__tx_store_zero_tail` 收尾时号码挂回槽表的空闲链头：后进先出，下一次分配即复用。
2. 运行时加固 H1：计数已为 0 再减即 4012“引用计数下溢”。号码已被复用时减的是新对象的计数，H1 看不到（加固设计 §二“不覆盖”）。
3. 测试专用页堆（`--generic=heapcheck`，设计 v052-heap-check）：每块独立映射、保护页、隔离区不复用地址、账本核对重复与非法释放。
   它只管分配器的块，“对象表这类大块内部的相邻槽”不在其列（§三-7）——对象号的复用正落在这里。页堆只在门里由生成器临时生成，
   经 `--link-object` 链接，用户手里没有。

## 二、对照

| 做法 | 例子 | 取舍 |
|---|---|---|
| 隔离区：释放的不立即复用，期间的访问与再释放可查 | ASan 的 quarantine；Zig GeneralPurposeAllocator 安全模式不复用地址；Objective-C 的 NSZombie（释放的对象换成僵尸类，再发消息即报） | 只在检测形态，发布零开销；窗口有限（隔离区满后照常复用） |
| 代数句柄：句柄带代数，槽复用时代数加一，旧句柄失配即报 | Rust 的 slotmap、游戏引擎的实体句柄 | 永久可查；句柄要有放代数的位、每次解引用核对 |
| 编译期杜绝 | Rust 所有权；太虚安全代码由编译器管理计数 | 安全代码本就不会过度释放；剩下的是运行时与编译器自身缺陷、不安全的外部函数用法 |

取隔离区：与页堆隔离地址同一思路，只动检测内核，发布内核逐字节不变；代数句柄留作后续（见第五节）。

## 三、做法

1. **对象号隔离（检测内核）**：页堆内核一律用可移植版槽表并开隔离（x86 的手写槽表没有隔离）。free 不再把号码挂回空闲链头：
   链项记“隔离中”0xFFFFFFFD、计数保持 0，号码入先进先出的隔离环（65536 项，与页堆的块隔离环相同；首次释放时分配，分配不了
   时这一个号码照常挂回空闲链，检查工具不另造失败）；环满时最早的号码才出环、挂回空闲链。槽表状态随之加三项 {隔离环@64,
   环首@72, 环内项数@80}，前 64 字节布局不变（RC 快路径、泄漏检查、调试视图照旧按它读；它们按链项是否为“在用”0xFFFFFFFE 判存活，
   隔离中的号码不算存活）。此间对它多出的一次释放落在计数为 0 的号码上，由 H1 报 4012；对隔离中的号码再 free 得 0（不在用）。
2. **用户入口**：`taixu build／run／test --heap-check` 链接检测内核（页堆＋对象号隔离），可与 `--leak-check`、`--debug` 同用；
   与 `--link-object` 互斥（检测内核已内嵌）；`bench` 不收（检测内核会扭曲测量）。LSP、MCP、编译画像照用标准内核。
3. **检测内核的来源：嵌入**。实测（2026-10-26，Windows）：四个检测内核共 1.57 MB，编译器 47.8 → 49.5 MB（+3.5%）；改为把内核
   生成器链进编译器按需生成，生成器单独编出 29.5 MB、链进的增量难控，每次生成 0.35–0.54 s。取嵌入：构建驱动（`build.tx`，及
   历史重放的 `nrt-bootstrap.py`）按名单多生成 `kernel-heapcheck.obj`、`kernel-linux-heapcheck.o`、`kernel-macos-heapcheck.o`、
   `kernel-macos-aarch64-heapcheck.o`（生成时加 `--generic=heapcheck`），`taixu.tx` 嵌入；自举的“D 再生成须与嵌入相同”随名单
   覆盖它们。
4. **报告**：沿用 `__tx_trap` 的 4012 出口（`[runtime:corrupt_code]`，退出码 3）：页堆的消息以 `heapcheck:` 开头，过度释放为
   “引用计数下溢”。
5. **标准内核不变**：标准形态的槽表发出代码与改前逐字节相同（四个目标的标准内核核对相同），用户产物不变。

## 四、验证

1. 隔离机制（独立 C 校验，三端）：槽表探针加 `quarantine` 形态（隔离环 64 项——测试分配器单次至多 1 MiB，小容量才能在其中测满环
   与出环；页堆内核为 65536，逻辑同一份），`slot-faults.c` 以 `-DSLOTS_QUARANTINE` 核对：隔离环分配失败退回空闲链、释放的号码
   进隔离且不复用、重复释放被拒、环满后最早的号码出环并被重新分配、销毁后账本平衡；负对照——同一组检查对标准形态的对象必须
   失败；macOS 两个架构另做 Mach-O 与 ELF 对照。
   页堆本身的 C 驱动与变异体此前只在 Windows、Linux 上跑；本批经页堆探针对象补到 macOS 两种架构（页堆设计第五节补记），
   `--heap-check` 在三端的检测内核都有独立的正控制与变异体。
2. 用户入口：cli 加 8 行（标准与检测两种构建、检测产物含检测内核、照常运行、与 `--leak-check` 同用、`test`、与 `--link-object`
   互斥、`bench` 不收）；页堆门步的产物控制与全量语料改经 `--heap-check`（验证的是用户拿到的那份内嵌内核）。
3. 本机（Windows）：全量语料在 `--heap-check` 下除页堆既有豁免 `thread-many`（超时）外与标准结果逐例相同；产物控制（越界写、块尾
   空隙、释放后写）在 `--heap-check` 下查出、标准内核下照常跑完。

## 五、局限与后续

1. 隔离窗口之外（之后又有 65536 次释放）的过度释放仍可能漏，同 ASan 的隔离区。
2. 内联在对象表里的字段经隔离中的号码读取不报（数据块在页堆里的，经它的访问会报）；隔离中的号码被 retain（复活）不报。
3. 代数句柄：值的第二个字低 32 位放号码，高 32 位若空可放代数，检测形态下每次解引用核对，可永久查出且覆盖第 2 条；需要改
   所有经号码的访问路径，另行评估（跟进第 26 条余项）。
4. 页堆本身每块两页、每次分配释放一到两次系统调用，慢且耗内存；超出时限或映射上限的用例照页堆的豁免清单处理。
